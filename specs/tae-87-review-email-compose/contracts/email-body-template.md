# Contract: Email Body Template (Plain Text via mailto)

**Feature**: [Review Email Compose](../spec.md) | **Date**: 2026-08-03 (v4 — no truncation, no heading separators, decisions numbered)

Defines the plain-text email body format generated by `email-formatter.ts` when the rep clicks the Email button. The formatter builds a `mailto:` URL that opens the default mail client with subject and body pre-filled.

---

## mailto URL Format

```
mailto:?subject={encodedSubject}&body={encodedBody}
```

- No `to`, `cc`, or `bcc` parameters — recipient fields are left empty per FR-006
- Both `subject` and `body` are encoded with `encodeURIComponent()`

### Subject Line

**Format**: `Meeting Follow-Up: {meetingTitle}`

**Source**: `summary.meetingTitle`

**Encoding**: `encodeURIComponent(subject)`

---

## Body Format

The body string (before URL encoding) follows this structure. All formatting uses plain-text conventions: UPPERCASE for headings (no separator line beneath them), sequential numbers for topics/decisions/action items, indented bullets for signal sub-groups, and blank lines for spacing.

```
Hi,

{narrative}


WHAT WE HEARD
Hot:
  * {signal.label}
  * {signal.label}

Warm:
  * {signal.label}

Cold:
  * {signal.label}


WHAT WAS COVERED
1. {topic}
2. {topic}
3. {topic}


WHAT WAS DECIDED
1. {decision}
2. {decision}


ACTION ITEMS
1. {owner}: {description} (Due: {dueDate || "TBD"})
2. {owner}: {description} (Due: {dueDate || "TBD"})
3. {side label}: {description}


Looking forward to our next steps.

Best regards,
{repName}
```

### Greeting

Always `Hi,` — the recipient is unknown at compose time (sender adds recipients manually).

### Section Headings

All section headings are UPPERCASE text only, with **no separator line** beneath them:

```
SECTION NAME
{content starts immediately on the next line}
```

### What We Heard (Signals)

Signals from `leadScore.detectedSignals` are grouped by weight category. Each weight group has a label line followed by indented bullet items:

```
Hot:
  * {signal.label}

Warm:
  * {signal.label}

Cold:
  * {signal.label}
```

- Omit a weight group if no signals match that weight
- Omit the entire section if `detectedSignals` is empty
- Signal weight labels use title case: `Hot:`, `Warm:`, `Cold:`
- Do NOT include the signal's `evidence` field — only `label`
- These sub-groups are the one exception to "numbered lists everywhere": weighted signal tags are not a sequential list, so they keep indented bullet markers

### What Was Covered (Topics)

Topics from `summary.topics` are rendered as a numbered list:

```
1. {topic}
2. {topic}
```

- Omit the entire section if `topics` is empty

### What Was Decided (Decisions)

Decisions from `summary.decisions` are rendered as a numbered list (changed from bullets to numbering for consistency with Covered/Action Items):

```
1. {decision}
2. {decision}
```

- Omit the entire section if `decisions` is empty

### Action Items

Next steps and commitments are merged into a single numbered list. Next steps appear first, followed by commitments.

- **Next steps**: `{owner}: {description} (Due: {dueDate || "TBD"})`
- **Commitments**: `{side label}: {description}` — where `kaffea_x` renders as "Kaffea-X" and `prospect` renders as "Prospect"

```
1. John Smith: Follow up on pricing proposal (Due: 2026-08-10)
2. Sarah Lee: Send technical documentation (Due: TBD)
3. Kaffea-X: Prepare custom demo environment
4. Prospect: Share integration requirements
```

- Omit the entire section if both `nextSteps` and `commitments` arrays are empty

### Sign-off

```
Looking forward to our next steps.

Best regards,
{repName}
```

The rep name is derived from `summary.attendees`: find the first attendee where `side === 'kaffea_x'` and use their `name`. If no KaffaX attendee exists, omit the name line and use only `Best regards,`.

---

## Section Omission Rules

| Section | Omit When |
|---------|-----------|
| Summary (narrative) | Never — narrative is always present (spec assumption) |
| What We Heard | `detectedSignals` array is empty |
| Hot/Warm/Cold sub-group | No signals with that weight |
| What Was Covered | `topics` array is empty |
| What Was Decided | `decisions` array is empty |
| Action Items | Both `nextSteps` and `commitments` arrays are empty |

When a section is omitted, its heading and content are both removed. No empty gaps or orphaned headings.

---

## No Truncation (per FR-014, SC-002)

**All content is always included in full.** There is no length-based truncation of any kind — no item caps, no `[... and N more]` notes, no narrative shortening.

The `mailto:` URL has no hard length ceiling enforced by this feature. Very large meetings (many signals, topics, decisions, or action items) may produce a long `mailto:` URL. This is an accepted tradeoff: zero data loss takes priority over URL length, per explicit clarification in `spec.md`. The rep can always edit the email body in the mail client before sending.

*Historical note: an earlier version (v3) of this contract introduced a 2,000-character truncation strategy. It was removed after conflicting with spec.md's Edge Cases and SC-002 (see `research.md` amendment).*

---

## Excluded Content (per FR-013)

The following internal sales metrics MUST NOT appear anywhere in the email body:

- Lead score band (HOT / WARM / COLD)
- Numeric score percentage
- Lead score rationale

Signal weight labels (`Hot:`, `Warm:`, `Cold:`) in the "What We Heard" section refer to the signal category, not the overall lead score band. This is acceptable per FR-008 which requires including the signal weight category alongside each detected signal.

---

## Special Character Handling

All dynamic content is encoded via `encodeURIComponent()` when placed into the `mailto:` URL. This handles all special characters automatically including `&`, `=`, `?`, `#`, newlines, and non-ASCII characters.

Within the plain-text body itself (before encoding), no HTML escaping is needed since the content is plain text, not HTML.

---

## Security Note

The `mailto:` URL is constructed from `MeetingRecord` data that has already been validated and stored. No raw AI output is concatenated directly into the URL — all content comes from validated records. `encodeURIComponent()` prevents parameter injection.
