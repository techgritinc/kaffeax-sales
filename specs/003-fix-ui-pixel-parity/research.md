# Phase 0 Research: Pixel-Perfect UI Parity

No entries in Technical Context were marked `NEEDS CLARIFICATION` — this is a well-scoped visual-fidelity correction against an existing, unchanged canonical prototype, with no new technology or architecture decisions to make. Phase 0 research therefore consists of the concrete comparison work needed to root-cause the reported discrepancies: reading the prototype's `kx-*` CSS rules and JSX class usage side by side with the current implementation. Each finding below is a **Decision** (what the corrected behavior must be), backed by exact line references in `Design/POC_Kaffea-X_Prototype.html` and the current source file.

## Finding 1 — Sidebar status-chip text color uses raw brand colors instead of dedicated tints

- **Decision**: The sidebar's per-row "Draft"/"CRM" status badge MUST use the prototype's dedicated on-dark text tints — `#A6E6CA` for the saved/CRM state and `#E6C778` for the draft state — as new named design tokens, not the existing `--green`/`--mustard` brand tokens.
- **Rationale**: Prototype `.kx-side-status.saved`/`.draft` (lines 434–435) set `color: #A6E6CA` / `color: #E6C778` — visually muted, higher-contrast-on-navy tints distinct from the raw brand colors (`--green: #41bb93`, `--mustard: #a4812d`). `src/features/meeting-library/components/sidebar-item.tsx:20-21` currently uses `text-green` / `text-mustard`, which resolve to the raw brand colors, not these tints. Background (`bg-green/[0.18]`, `bg-mustard/[0.18]`) and border (`border-green/[0.35]`, `border-mustard/40`) already correctly derive from `--green`/`--mustard` opacity variants and match the prototype's `rgba(65,187,147,0.18|0.35)` / `rgba(164,129,45,0.18|0.4)` — only the solid text color is wrong.
- **Alternatives considered**: Reusing `text-green`/`text-mustard` as-is (rejected — visibly wrong color, fails Principle XII); hardcoding the hex directly in the component (rejected — violates Principle II's zero-tolerance for hardcoded colors). The correct path is a new token pair (e.g. `--sidebar-status-saved-text`, `--sidebar-status-draft-text`) added to `globals.css` and registered via `@theme inline`, per the constitution's token workflow.

## Finding 2 — Sidebar row vertical spacing is missing

- **Decision**: Each sidebar item row MUST have a 2px vertical margin (top and bottom) in addition to the existing 8px horizontal margin.
- **Rationale**: Prototype `.kx-side-item` (line 458) sets `margin: 2px 8px` (vertical 2px, horizontal 8px). `src/features/meeting-library/components/sidebar-item.tsx:33` applies `mx-2` (8px horizontal) only — no vertical margin class is present, so adjacent rows sit flush against each other instead of the prototype's small gutter.
- **Alternatives considered**: Adding a `gap`/`space-y` wrapper around the mapped items in `sidebar.tsx` instead of a per-item margin (rejected — the prototype applies the margin to the item itself via `.kx-side-item`, and per-item margin also correctly produces the leading/trailing edge gutter above the first and below the last item in each group, which a wrapper `gap` would not).

## Finding 3 — Capture screen hero accent bar uses the wrong variant, color, and size

- **Decision**: The capture screen's hero `AccentBar` MUST render the midnight-colored bar (matching the prototype's default `.kx-accent-bar`/`h1` styling), sized 112×10 at desktop width and shrinking only in *size* — never color — at narrower breakpoints (96×8 at the tablet breakpoint, 72×6 at the mobile breakpoint), not the fixed-size bright-blue `h2` bar it currently renders.
- **Rationale**: The prototype's shared `Hero` component (lines 2903–2912) always renders a plain `.kx-accent-bar` div — the base rule (line 506–510: `width:112px; height:10px; border-radius:2px; background: var(--midnight)`). The scoped override `.kx-capture-hero .kx-accent-bar` (lines 776, 834, 847) only changes `margin`/`width`/`height` at breakpoints — it never changes `background`. `src/features/meeting-capture/components/capture-screen.tsx:21` instead renders `<AccentBar variant="h2" className="my-[10px]" />`, which maps to `bg-bright-blue h-[6px] w-[72px]` (`src/components/ui/typography/accent-bar.tsx:17`) — the wrong color (bright blue instead of midnight) and a fixed size that only happens to match the *smallest* mobile breakpoint, with no responsive resizing at wider viewports.
- **Alternatives considered**: Leaving `variant="h2"` and just changing its color (rejected — `h2`/bright-blue is a distinct, correctly-used variant elsewhere, e.g. `processing-modal.tsx`'s `Heading level={2}`; conflating the two variants would break that usage). The fix is to use `variant="h1"` here and add the missing responsive size behavior (see Finding 4).

## Finding 4 — `AccentBar` encodes no margin, so every call site improvises spacing independently

- **Decision**: `AccentBar` (or its call sites, consistently) MUST reproduce the prototype's per-context margin rules rather than leaving margin to be added ad hoc per usage: `.kx-accent-bar` (generic `Hero`, e.g. commit screen) → `margin: 12px 0 16px`; `.kx-bar-h1` (used for other `h1`-styled contexts) → `margin: 14px 0 12px`; `.kx-bar-h2` → `margin: 8px 0 16px`; `.kx-capture-hero .kx-accent-bar` → `margin: 10px 0 10px` at base, shrinking further at the mobile breakpoint.
- **Rationale**: `src/components/ui/typography/accent-bar.tsx` sets only `bg-*`/`h-*`/`w-*`/`rounded-tight` — no margin at all. As a result: `commit-screen.tsx:31` renders `<AccentBar />` with **zero** margin (prototype expects `12px 0 16px`); `processing-modal.tsx:53` renders `<AccentBar variant="h2" />` with zero margin on the bar itself, instead relying on the following paragraph's `mt-[10px]` to approximate spacing (prototype expects the bar itself to carry `8px 0 16px`); `capture-screen.tsx:21` bolts on `className="my-[10px]"` to approximate the capture-hero override. `chat-panel.tsx:59` reproduces a `kx-bar-h2`-equivalent element inline (`rounded-tight bg-bright-blue mb-4 h-1.5 w-[72px]`) with only a bottom margin (`mb-4` = 16px) and no top margin, missing the `8px` top margin `.kx-bar-h2` requires.
- **Alternatives considered**: Continuing to let each call site set its own margin via `className` (rejected — this is precisely the pattern that produced the current drift across four separate call sites, and offers no single source of truth to verify against the prototype). The corrected approach folds each context's margin into a small set of variants/props on the shared component (or a documented per-context class token), so every usage of a given visual context automatically gets the correct spacing.
